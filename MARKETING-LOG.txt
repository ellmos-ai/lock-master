1. REPOSITORY AUDIT & DISCOVERABILITY BASELINE
================================================================================
- Organization: ellmos-ai
- Ecosystem: open-bricks (umbrella)
- Target Audience: Multi-agent developers, AI agent system architects, offline-first engineers, multi-machine operators, infrastructure reliability teams
- Core Positioning: Portable, zero-dependency file-based mutex and coordination protocol for AI coding agents (Claude Code, Codex, Antigravity/Gemini) and humans sharing workspaces.
- Distinct Value Proposition: Operates entirely via transparent, human-readable plain text files (LOCK*.txt). Requires zero daemons, zero external databases (no Redis, no Consul), and runs on pure Python standard library (3.10+). Features cloud-sync tolerance, team locks with intra-host sub-claims, and declarative access permissions.
- Sibling Ecosystem Integration: Foundational locking and synchronization pillar in the ellmos infrastructure stack alongside ticket-master (task triage), system-gap-master (cross-machine sync yard), agent-ops-stack, and sqlite-transit-sync.

================================================================================
2. TARGET PERSONAS & USER JOURNEYS
================================================================================
1. Autonomous AI Agent Architects & Fleet Coordinators
   - Needs: Coordinate multi-agent swarms (Codex, Claude Code, Gemini/Antigravity) operating on local git checkouts and shared file trees without race conditions or destructive overwrites.
   - Pain Points: Conventional distributed lock managers (Redis Redlock, etcd, Zookeeper) require heavyweight daemons, complex credentials, and fail completely in offline or local-first environments.
   - lock-master Solution: Plain text `LOCK*.txt` files that any agent or language can read and write. Scoped locks (`LOCK.<scope>.txt`) allow fine-grained concurrency across independent submodules.

2. Multi-Device & Cloud-Sync Developers
   - Needs: Work across multiple physical computers (laptop, workstation, server) synchronized via OneDrive, Dropbox, or Syncthing without corrupted lock states.
   - Pain Points: Traditional file-locking APIs (OS flock, fcntl) do not propagate across cloud sync folders, and latency (30s to 5min) causes conflicting edits.
   - lock-master Solution: Dedicated Team Locks (`LOCK.team.<host>.txt`) per physical machine that inform peer systems to stay out, coupled with rename-based atomic file claims.

3. Local-First & Zero-Egress Tool Builders
   - Needs: Build secure, compliant developer tools and MCP servers that operate in strictly air-gapped, zero-telemetry environments.
   - Pain Points: Cloud-managed orchestration tools phone home, transmit telemetry, and require network access for authentication.
   - lock-master Solution: 100% Local-First / Zero-Egress, unprivileged user-mode (`RunAsInvoker`) operation, and zero external runtime dependencies (Python standard library only).

4. Enterprise Security, Privacy & Safety Officers
   - Needs: Guarantee fail-closed access control, auditable permission rules, transparent lock status, and reproducible recovery from abandoned processes.
   - Pain Points: Opaque locking databases hide who holds which lock and why, making deadlocks difficult to debug.
   - lock-master Solution: Human-readable metadata (owner, host, purpose, expiry, condition), declarative `LOCK.permissions.json` evaluation, safe dry-run stale pruning (`prune_stale_locks.py`), and 10 codified governance invariants (`INV-LOCAL-01` to `INV-SLA-10`).
